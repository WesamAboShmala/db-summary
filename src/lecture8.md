🛡️ محاضرة Backup and Recovery Concepts
1) ليش هاد الموضوع "الأهم" بالمادة؟
هاد آخر جزء بمادة Database Security، وهو الجزء الأهم. ناس كتير بتعتبر exp/imp أو Data Pump "باك أب وريكفري" وهالكلام مش صح.
🚨 الريكفري الحقيقي = ريكفري لكل قاعدة البيانات، مش للبيانات اللي جواها بس.
الفرق العملي بينهم:
•	لو اعتمدت على Data Movement (export) للريكفري: لازم أنشئ قاعدة بيانات جديدة، Instance جديد، Configuration جديد، وبعدين أعمل Import ➔ هاد بيسبب Downtime كبير غالبًا غير مقبول.
•	الباك أب للبيانات (exp/imp): مفيد بس بحالات محدودة: فقدت يوزر، بدي أرجع جدول، بدي أرجع سكيما أو Object واحد مش قادر أرجع القاعدة كلها منه.
•	لو صار Disaster Recovery (كارثة كبيرة، السيرفر كله ضرب، بدي أرجع القاعدة كلها): هون يفضّل نستخدم Backup and Recovery Concept الحقيقي.
2) تذكير بمعمارية القاعدة (Architecture)
نفس رسمة أول محاضرة بالمادة:
•	Instance: الذاكرة والعمليات اللي شغالة.
•	Database: الملفات (Control File, Redo Log File, Data File, Parameter File).
📌 النقطة المهمة: لما نحكي "باك أب للداتابيز"، بالحقيقة بنحكي عن باك أب للـ Instance + باك أب للـ Database مع بعض... مش بس نسخ ملفات عشوائية.
3) سبب وجود Backup/Recovery أصلًا: User Error
رجوع لتصنيف قديم:
•	Logical Error (خطأ منطقي، زي حذف غلط): ممكن أحله بـ Flashback أو طرق تانية.
•	Physical Corruption (تلف فيزيائي: هارد ديسك اتعطل، فايروس شفّر الملف، Bad Sector): ما في حل سريع الحل الوحيد Recovery: آخذ نسخة احتياطية وأرجّعها.
4) الباك أب "التام" مش بس اتخاذ الخطوات الصحيحة (نصيحة أساسية)
مش مجرد إنك أخذت عملية باك أب بخطوات صحيحة يعني الباك أب "تام".
لازم يتم فحص الباك أب (Backup Testing) منصوص عليه بالـ Policy: الباك أب بياخذ يوميًا/أسبوعيًا، وبيتم فحصه فعليًا (حدا بيسترجع النسخة على سيرفر تجريبي، يتأكد إن البيانات والـ Records مضبوطين).
•	النسخة اللي اتفحصت وثبت نجاحها = "Tested".
•	لازم يكون عندي على الأقل نسخة واحدة Tested، حتى لو عندي نسخة أحدث لسه ما اتفحصتش.
•	السبب: لو صار تلف بالنسخة الأحدث، بضل عندي نسخة قديمة مضمونة ومجربة أرجع لها.
5) الفرق بين "الداتابيز طافية" و "Instance Failure"
عند إطفاء الـ Instance (Service تبع أوراكل): البيانات (Data Files) موجودة وسليمة، بس الـ Instance نفسه مش شغال. هاد بالضبط معنى Instance Failure.
⚠️ أسباب Instance Failure:
•	انقطاع كهرباء مفاجئ.
•	Hardware Failure.
•	فيروس عطّل الـ OS أو الـ Services.
•	يوزر عمل Kill لكل الـ Sessions.
•	تعطّل Critical Background Process.
6) الـ Background Processes (لازم أعرف أهمها)
العملية	وظيفتها
SMON / PMON	System Monitor / Process Monitor بيراقبوا الـ Instance
ARCn (Archiver)	بيعمل أرشفة مهم بس لو القاعدة بوضع Archive Mode
LGWR (Log Writer)	بيكتب على الـ Redo Log File
CKPT (Checkpoint)	بيعمل "مزامنة" (Synchronization) بين الثلاث فايلات
DBWR (DB Writer)	بيكتب على الـ Data File
🔴 الشرط الأساسي: الثلاث فايلات (Control File, Redo Log File, Data File) لازم يكون عندهم نفس رقم SCN (System Change Number) عشان القاعدة تشتغل صح.
7) أنواع الـ Shutdown
النوع	شو بيعمل	ملاحظة
Shutdown Normal	بيستنى كل الـ Transactions والـ Sessions تخلص، بعدين يطفي	أفضل نظريًا، بس غير عملي، محدا بيستخدمه
Shutdown Immediate	بيعمل Rollback لأي Transaction مفتوحة، ويطفي بطريقة سلسة	الأكثر استخدامًا، ما في مشاكل
Shutdown Abort	إطفاء عاجل/طارئ فوري	بس بحالات طوارئ حقيقية، وبيحتاج Instance Recovery لما أرجع أشغلها
8) شو هو Instance Recovery؟ (أهم جزء تقني بالمحاضرة)
لما أعمل Shutdown Abort، ممكن يكون في Redo موجود بالـ Redo Log Files بس لسه ما انكتبش على الـ Data File. هون بيصير Instance Recovery، وبيعتمد على آلية الـ Checkpoint:
1.	الـ Checkpoint بيقارن الـ SCN بين الثلاث فايلات.
2.	لو مش متساويين، بيروح يجيب من الـ Redo Log File المعلومات الناقصة ويطبّقها على الـ Data File عشان توصل الكل لنفس الرقم (Synchronization).
متى يشتغل الـ Checkpoint؟ عند كلمة COMMIT، أو كل 30 ثانية.
🔄 آلية الكتابة بالتفصيل (Write-Ahead Logging)
UPDATE Statement ➔ تُكتب في Redo Log (قبل Commit) ➔ COMMIT ➔ CKPT يوجّه DBWR ➔ تُكتب في Data File
1.	أعمل جملة UPDATE مثلًا ➔ بتنكتب بالـ Redo Log File أول (حتى قبل الـ Commit).
2.	لما أعمل COMMIT، تصير الجملة "Committed" بالـ Redo Log.
3.	الـ Checkpoint بيشتغل (عند الـ Commit أو كل 30 ثانية)، وبيأمر الـ DBWR ينقل الأثر من الـ Redo Log للـ Data File الفعلي.
عند الـ Instance Recovery: النظام بيروح عالـ Redo Log File، بيشوف الجمل:
•	إذا Committed ➔ ينفذها (يطبقها على Data File).
•	إذا Uncommitted ➔ يعمل لها Rollback (باستخدام بيانات الـ Undo).
✍️ الـ LGWR (Log Writer) بيشتغل بـ 3 حالات:
1.	عند Commit أو Rollback.
2.	لما ثلث الملف (Redo Log File) يمتلئ.
3.	قبل ما يشتغل الـ DBWR (يكتب على Data Files) لازم الـ LGWR يكون خلّص كتابته أول (مبدأ Write-Ahead Logging: الـ Log لازم ينكتب قبل التغيير الفعلي).
9) الـ Archiver ووضع Archive Log Mode
الداتابيز عندها أكثر من Redo Log File (اثنين على الأقل، ممكن 3، 4، 5...) وبتشتغل عليهم بشكل دوري (Cyclical) لما يمتلئ واحد، تنتقل للتاني، ولما تخلص كلهم بترجع للأول.
❓ السؤال: لما يمتلئ الملف وبدي أكتب فوقه ثاني مرة، شو بصير بالبيانات القديمة اللي فيه؟
•	إذا Archive Log Mode مفعّل: قبل ما يُكتب فوق الملف، بينحفظ (يُؤرشف) نسخة منه بمكان تاني ➔ القاعدة بوضع Archive Log Mode.
•	إذا مش مفعّل: بينكتب فوق البيانات القديمة مباشرة ➔ القاعدة بوضع No Archive Log Mode.
💡 التوصية: لازم القاعدة تكون بوضع Archive Log Mode، لأنه:
1.	بيوسّع نطاق الـ Recovery (بدل ما أكون محصور بس بالـ 3 فايلات الدائرية، عندي أرشيف كامل التاريخ).
2.	أداة RMAN (أداة الباك أب الاحترافية) بتحتاج القاعدة تكون بهاد الوضع عشان تشتغل صح.
10) مثال توضيحي على الـ Instance Recovery بالأرقام (SCN)
مثال بأرقام:
•	Data File: كان عند SCN=99، صار 129، صار 140.
•	Control File: عند SCN=143.
•	Redo Log File: يغطي مدى من 74 إلى 143.
العملية: بما إن الـ Control File هو "المتحكم" (الأعلى)، النظام بيروح عالـ Redo Log ويجيب البيانات الناقصة (Committed) ويطبقها على الـ Data File لحد ما توصل لنفس رقم الـ Control File (143).
بعد ما تتزامن الثلاثة، لازم أعمل Reset Logs عملية بترجّع ترقيم الـ SCN من جديد للثلاث فايلات.
↕️ اتجاهين للـ Instance Recovery:
•	Forward (للأمام): الوضع الطبيعي والمفضّل من SCN أقل لأعلى (زي 99 ➔ 144).
•	Backward (للخلف): لو انفقد الـ Redo Log File، بضطر أرجع للوراء وهاد معناه فقدان بيانات (Data Loss).
🔴 القاعدة الذهبية: كل ما كان عندي Archive Log أكتر، كل ما كانت مساحة الـ Recovery تبعي أوسع، وقل احتمال إني أضطر أرجع للخلف وأخسر بيانات.
11) Multiplexing (تكرار/نسخ الملفات الحرجة)
لتقوية الـ Recovery، لازم:
•	أكتر من Redo Log Group، وكل مجموعة تكون نسخة من الثانية لو انفقدت وحدة، توجد الثانية.
•	Control File برضه لازم يكون Multiplexed (أكتر من نسخة بمكان تاني) عرض عملي بيّن إنه في نسخة من الـ Control File بمكانها الأصلي، ونسخة تانية جوا الـ Flash/Fast Recovery Area.
12) مقدمة عن Fast Recovery Area (FRA)
(مجرد تعريف اسم، التفاصيل بمحاضرات جاية)
مكان مركزي بيحتوي:
•	Archive Log
•	Backup Sets

13) نوعين من طريقة أخذ الباك أب: Image Copy مقابل Backup Set
المعيار	Image Copy	Backup Set
الفكرة	نسخة طبق الأصل، كل ملف مقابل ملف بمكان تاني	كل الملفات مجمّعة/مضغوطة بملف أو أكتر حسب الحجم
السرعة بالاسترجاع	أسرع (Downtime أقل بس تغيير أسماء وتوجيه)	أبطأ نسبيًا
الحجم	أكبر (نسخة طبق الأصل لو الملف 40 جيجا فيزيكاليًا صارت نسخته 40 جيجا، فيصير المجموع 80)	أصغر (بسبب الضغط لو الملف فيزيكاليًا 40 جيجا بس المُعبّى فيه فعليًا 20 جيجا، الـ Backup Set بياخذ ~20 جيجا بس)
وقت الباك أب/الريكفري	أسرع	أبطأ (بسبب الضغط)
Portability	أقل (ملفات كتير منفصلة)	أعلى (ملف أو اثنين بس بدل 10)
❓ مين أحسن؟ ما في شي أفضل من شي بشكل مطلق كل تكنولوجيا إلها مزايا وعيوب، والمهندس بيقرر بناءً على موارده وإمكانياته وسياسة الشركة (Policy)، مش بيتبع خطوات جاهزة بس.
"المهندس ما بينفذ خطوات، المهندس بياخذ قرارات."
14) استراتيجية Full مقابل Incremental Backup
أخذ الباك أب الكامل (Full) كل يوم مش منطقي لقاعدة بيانات كبيرة (بيهلك الموارد). الحل: استراتيجية مركّبة:
•	Level 0: نسخة كاملة (Full) أساس الاستراتيجية (مثلًا يوم السبت).
•	Level 1, 2, 3...: تغييرات لاحقة بس (Incremental)، وفيها نوعين:
📈 Incremental Cumulative (تراكمي)
كل مرة باخذ كل التغييرات من آخر Level 0 لحد الآن.
•	مثال: سبت=Level 0، أحد=(تغييرات من السبت)، اثنين=(تغييرات من السبت)، ثلاثاء=(تغييرات من السبت)...
•	حجم النسخ بيكبر تدريجيًا كل يوم.
•	ميزة الريكفري: بس محتاج آخر Level 1 + Level 0 عملية استرجاع أبسط وأسرع.
📉 Incremental Differential (تفاضلي)
كل مرة باخذ بس التغييرات من آخر نسخة سابقة (أيًا كان مستواها)، مش من الـ Level 0 دايمًا.
•	مثال: سبت=Level 0، أحد=Level 1 (تغييرات من السبت بس)، اثنين=Level 2 (تغييرات من الأحد بس)، ثلاثاء=Level 3 (تغييرات من الاثنين بس)...
•	حجم كل نسخة صغير (لأنها بس تغييرات يوم واحد).
•	عيب الريكفري: محتاج كل السلسلة كاملة (Level 0 + 1 + 2 + 3...) عشان أرجّع البيانات سلسلة أطول.
❓ مين أحسن؟ برضه ما في جواب مطلق قرار استراتيجي.
💡 النصايح المهمة:
1.	ما تاخذ Full كل يوم بيهلك الموارد.
2.	لازم يكون عندك نسختين دائمًا: وحدة Tested وواحدة Not Tested (خصوصًا الـ Level 0 لازم يكون Tested دايمًا كحد أدنى مضمون).
3.	الـ Backup Policy لازم تكون معتمدة من الإدارة، مش قرار شخصي للمهندس فيه شركات بتاخذ Level 0 يوم الخميس، وناس يوم الاثنين، وناس يوم السبت القرار حسب السياسة المعتمدة.
15) Offline Backup مقابل Online Backup
•	Offline (Cold) Backup: أطفي القاعدة، أنسخ الـ Data Files لمكان تاني، أشغّل القاعدة ثاني. أبسط طريقة، بس مش موصى فيها (بتحتاج Downtime وإطفاء).
•	Online (Hot) Backup: آخذ نسخة والقاعدة شغالة بدون توقف، وبقدر أعمل لها Recovery بأي وقت. هاي الطريقة المفضّلة/الموصى فيها.
القاعدة بتتكون من Instance (عمليات) و Database (ملفات)، ولازم الملفات التلاتة (Control/Redo/Data) تضل متزامنة برقم SCN، وأي عطل بسيط بيتصلّح تلقائيًا عبر Instance Recovery (باستخدام Checkpoint والـ Redo Logs)، أما أي كارثة حقيقية (فقدان القاعدة كلها) بتحتاج استرجاع نسخة احتياطية حقيقية مُختبرة (Tested) والاستراتيجية (Image Copy أو Backup Set، Full أو Incremental، Cumulative أو Differential، Online أو Offline) قرار هندسي مبني على موازنة الموارد والاحتياجات وسياسة الشركة، مش خطوات ثابتة واحدة تناسب الجميع.
