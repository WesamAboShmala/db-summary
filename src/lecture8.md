محاضرة Data Movemen
1) شو هو Data Movement أصلًا؟
	الموضوع فرعي من موضوع أكبر اسمه Availability (توفر البيانات)، جاي بعد Undo Management و Flashback.
	تعريفه: أنا باخذ بس البيانات اللي جوّا القاعدة (Objects: جداول، بيانات...) وبصدّرها لملف على نظام التشغيل، وبقدر أرجعها لنفس القاعدة أو لقاعدة تانية.
❓ ليش سُمّي "Movement"؟
لأنه البيانات بتتحرك بمسار:
"Database"⟶"OS"⟶"(فلاش/هارد ديسك)"⟶"Database ثانية" 
2) أهم فرق مفاهيمي: Data Movement ≠ Backup، و Data Backup ≠ Database Backup
هاي أهم نقطة بكل المحاضرة، وفيها 3 مستويات لازم أفرّق بينهم:
	Database Backup الحقيقي: نسخة من ملفات قاعدة البيانات الفيزيائية نفسها.
	Data Backup (وهو اللي بيعمله exp/imp): نسخة من البيانات اللي جوّا القاعدة بس، مش من القاعدة نفسها.
الفرق العملي بينهم عند الكارثة:
	لو صار DROP DATABASE بالكامل:
	مع Data Backup لازم:
	أنشئ قاعدة بيانات جديدة من الصفر.
	أعيد ضبط كل الـ Parameters والإعدادات يدويًا واحد واحد.
	بعدين أعمل import للبيانات.
	مع Database Backup حقيقي: برجّع كل شي (ملفات + إعدادات + بيانات) بعملية واحدة.
❓ مين أحسن؟ يعتمد على إتقاني: متقن الـ Export أشتغل عليه، متقن أداة زي RMAN أشتغل عليها. المهم الإتقان مش الأداة بحد ذاتها.
⚠️ خلاصة الفكرة: exp/imp ممكن أستخدمها كاستراتيجية باك أب، لكن مش موصى فيها كحل أساسي وحيد للـ Backup بسبب الوقت (بيزيد مع حجم القاعدة)، وبسبب إنها بترجعني بس لآخر وقت أخذت فيه نسخة (مش بدقة اللحظة زي Flashback).
🔄 تذكير سريع Flashback:
	Physical Corruption (تلف بالملفات): لازم أرجع لملفات OS، الـ Flashback ما بينفع.
	Logical Corruption (خطأ منطقي زي حذف غلط): أقدر أستخدم Flashback.
3) مين يملك صلاحية Data Movement؟
(لازم أفهمها قبل ما أبلش بالتطبيق)
Data Movement من أهم مهام الـ DBA، وما بتُعطى لأي Programmer.
	السبب: أي حدا ياخذ ملف dump ويعمل عليه import كامل بقاعدة تانية، رح يقدر يشوف كل اليوزرات والجداول والبيانات بغض النظر عن الصلاحيات الأصلية.
"Data Security"\xleftrightarrow"علاقة عكسيةData Movement" 
بمجرد تصدير البيانات من الداتابيز لملف OS، بتخسر كل طبقات الأمان (Grants/الصلاحيات) المبنية على مستوى القاعدة.
💡 مثال: لو ما عندي صلاحية أستعلم على جداول قسم Finance، بس أخذت ملف الـ dump ورجّعته بقاعدة تانية عندي، بقدر أشوفها عادي.
4) الأدوات: جيلين
الجيل القديم: exp / imp (Legacy)
	بتشتغل من CMD (مش من جوّا SQL*Plus).
	exp = تصدير، imp = استيراد.
	آلية الشغل مبنية على SQL.
	الهدف الرسمي: Extract Data to External File مش Backup بحد ذاتها.
Bash
exp system/password@orcl file=D:\backup\full.dmp full=y
	file= ← وين حيتخزن ملف الإخراج (بامتداد .dmp).
	full=y ← صدّر كل الـ Objects الموجودة بقاعدة البيانات.
🚀 الجيل الحديث: expdp / impdp (Data Pump)
	أسرع بكتير من exp/imp.
	آلية الشغل مبنية على API مش SQL.
	الهدف الرسمي: نفس فكرة الـ Legacy (Extract/Load) بس بآلية أحدث وأقوى.
جدول مقارنة Legacy مقابل Data Pump
الفرق	exp/imp (Legacy)	expdp/impdp (Data Pump)
الآلية	SQL	API
الأداء	أبطأ	أسرع بكتير
Compression	❌	✅ (لتقليل الحجم وتسريع النقل عبر الشبكة/تخزين خارجي)
Network Mode	❌	✅ (تشتغل عن بعد مباشرة عبر Remote Session)
الفلترة	بسيطة	متقدمة
التحكم بالصلاحيات	محدود	أدق
⚠️ علاقة عكسية بالـ Compression: كل ما ضغطت أكتر (حجم أصغر)، كل ما أخذ وقت و CPU أعلى بس النتيجة النهائية نفسها.
💡 نصيحة: "لو بدك تتعلم حاجة، تعلّم Export DP/Import DP، وانسى Export/Import Legacy تمامًا ما رح تحتاجها بالشغل الحقيقي." الـ Legacy كان بس لتبسيط فهم السيناريو الأساسي.
📁 الفرق الجوهري بالاستخدام: Directory Object (خاص بالـ Data Pump)
Export DP/Import DP ما بتتعامل مباشرة مع الـ File System (عكس exp/imp اللي بتاخذ مسار مباشر file=D:\...). لازم Object وسيط جوا القاعدة اسمه DIRECTORY يمثل مسار فيزيائي على نظام التشغيل، وأدي صلاحيات READ/WRITE عليه لليوزر قبل ما أقدر أستخدمه.
SQL
CONNECT SYSTEM;
CREATE DIRECTORY dair AS 'C:\export_dp';
GRANT READ, WRITE ON DIRECTORY dair TO user;
📌 تشبيه مهم: الـ DIRECTORY هو Object منطقي بالضبط زي Tablespace — إطار منطقي (Logical Framework) مش تعامل مباشر مع مسار.

النوع	يصدّر شو؟

Schema	يوزر/سكيما معينة بس

6) السيناريو العملي بالـ Legacy (exp/imp) خطوة خطوة
الفكرة: محاكاة "حذف يوزر بالغلط" وطريقة استرجاعه بدون Flashback.
1. أخذ نسخة كاملة قبل أي مشكلة
Bash
exp system/password@orcl FULL=Y FILE=full_backup.dmp LOG=full_backup.log
	FULL=Y ← صدّر كل الأوبجكتس بالقاعدة.
	FILE= ← مسار ملف الـ dump الناتج.
	LOG= ← ملف يسجل نتيجة العملية.
2. محاكاة الكارثة (حذف اليوزر بالغلط)
SQL
DROP USER ashaat CASCADE;
3. إنشاء يوزر جديد فاضي لاستقبال البيانات
SQL
CREATE USER new_ashaat IDENTIFIED BY strongpassword;
GRANT RESOURCE, CREATE SESSION TO new_ashaat;
4. الاسترجاع الانتقائي (مش رجوع القاعدة كلها!)
Bash
imp system/password@orcl FILE='d:\exp\full.dmp' FROMUSER=ashaat TOUSER=new_ashaat
💡 النقطة الذكية: رغم إني صدّرت القاعدة كاملة، وقت الاسترجاع كنت انتقائي طلعت بس بيانات "ashaat" من الملف الكبير وحطيتها بيوزر تاني. تصدير شامل + استرجاع دقيق ومحدد.
5. فحوصات بعد الاستيراد (ما أكتفي بفحص عشوائي)
SQL
SELECT object_type, COUNT(*) FROM user_objects GROUP BY object_type;
SELECT * FROM some_table;
	الاستعلام الأول بيديني ملخص شامل لكل أنواع الكائنات اللي رجعت أتأكد إن كل شي رجع مش بس جدول واحد.
	لازم أتأكد كمان من عدم وجود Invalid Objects و صلاحيات ناقصة (grants ممكن ما ترجعش أوتوماتيك).
7) فروقات الـ Syntax والبارامترات
فروقات الـ Syntax بين الاثنين:
المفهوم	Legacy	Data Pump
مسار الملف	FILE=	DUMPFILE= (+ لازم DIRECTORY=)
ملف السجل	LOG=	LOGFILE=
المالك	OWNER=	SCHEMAS=
الجداول	TABLES=	TABLES= (نفسه)
📌 الفرق الجوهري الوحيد المهم فعلاً = موضوع الـ DIRECTORY Object.
بارامترات إضافية بالـ Data Pump (عيّنات للتجربة):
	ROWS=Y/N: بدي البيانات فعليًا ولا بس هيكلية الجداول فاضية؟
	FULL: تصدير القاعدة كاملة.
	CONSISTENT: لو عندي جداول مرتبطة بـ Foreign Keys، بيضمن تصديرهم مع بعض للحفاظ على التناسق ما بتصدّر واحد من غير التاني المرتبط فيه.
	COMPRESSION: الضغط (Data Pump بس).
	GRANTS=Y/N: هل تُنسخ الصلاحيات الممنوحة على الكائن معه؟
	INDEXES=Y/N: هل تُنسخ الـ Indexes؟
	TRIGGERS=Y/N: هل تُصدَّر الـ Triggers؟
(كلها Samples لازم أعدّلها حسب قاعدة بياناتي أنا)
8) الجانب الأمني الكامل (Security) 
⚠️ المخاطر:
	سرية البيانات (Confidentiality): ملف الـ dump نفسه = نسخة كاملة من بياناتي الحساسة موجودة كملف عادي على الهارد ديسك!
	تخزين غير آمن لملفات الـ dump.
	ضعف التحكم بالوصول (Access Control) لهاي الملفات.
	الحاجة للـ Encryption وصلاحيات محكمة.
فصل الصلاحيات: OS Administrator مقابل Database Administrator
	ممنوع أعطي الـ OS Administrator اليوزرنيم/باسورد تبع DBA أو SYSDBA لأنه بهيك الحالة بيصير هو "مالك" فعلي لكل الداتابيز (لأنها بالنهاية ملفات على نظام التشغيل اللي هو مسؤول عنه). ممكن أحط قيود، بس جوهريًا صار وصوله كامل.
	الحل: Safe Storage محدودة الوصول لملف الـ dump.
	التشفير: القاعدة ما بتطلّع الملف مشفّر تلقائيًا لازم أداة تشفير Third-Party بعد ما يطلع الملف، وخصوصًا وقت نقله لمكان تاني. بعد ما يطلع الملف، التحكم بالوصول بيصير مسؤولية OS مش القاعدة.
🛡️ أفضل الممارسات الأمنية (Best Practices):
	تجنّب استخدام حسابات SYS/SYSTEM لعمليات Data Movement. أنشئ يوزر مخصص بصلاحيات DBA محدودة واستخدمه بدلًا منهم.
	تشفير ملفات الـ dump عند الإمكان (أداة خارجية).
	صلاحيات مجلد Data Pump Directory لازم تكون متفق عليها بين DBA و OS Administrator مع بعض، مش قرار طرف واحد.
	حذف الملفات المؤقتة فورًا بعد الاستخدام.
🎯 الأمان ما بيوصل 100%، بس الهدف "تحسين مستمر" قد الإمكان.
🤖 9) فكرة الأتمتة (Automation) + أهمية ملف اللوج
	أقدر أحط أوامر الـ export جوا ملف Batch (.bat).
	أربطه بـ Task Scheduler على ويندوز، وأحدد له وقت تنفيذ يومي (مثلاً كل يوم 4 عصرًا).
	بيشتغل أوتوماتيك حتى لو ما في حدا قاعد قدام الجهاز، طالما السيرفر شغال.
📝 لكن لو معتمد على الـ export كاستراتيجية باك أب، لازم أراجع اللوج دائمًا:
	أتأكد ما صار Termination بمنتصف العملية (زي انقطاع كهرباء).
	أتأكد حجم الملف طبيعي وحتى لو طبيعي، برضه لازم أراجع اللوج.
💡 نصيحة: ما أعتمد على استراتيجية باك أب واحدة بس أعتمد أكتر من واحدة (2-3 طرق) عشان ما يصير عندي نقطة فشل واحدة. ميزة الـ Export إنها خفيفة على القاعدة والسيرفر، فتصلح كطبقة حماية إضافية.
🎯 خلاصة نهائية بجملة وحدة أقولها لحالي
exp/imp و expdp/impdp أدوات لاستخراج (Extract) "صورة" من محتوى قاعدة البيانات بلحظة معينة وتخزينها كملف على نظام التشغيل، وبقدر أرجعها كلها أو جزء منها بمرونة عالية بس هاي العملية سلاح ذو حدين: مفيدة جدًا للاسترجاع الانتقائي، لكنها بتخلق ملف حساس بيفقد كل صلاحيات وأمان القاعدة الأصلية، لازم أحميه بصلاحية محدودة وتشفير خارجي، وما لازم أعتمد عليها لحالها كبديل كامل عن Database Backup حقيقي (لأنها Data Backup مش Database Backup) وهاي الصلاحية بالأساس حكر على الـ DBA، مش أي مبرمج. وبالشغل الفعلي، الأفضل أعتمد Data Pump (expdp/impdp) وليس Legacy (exp/imp).
